# Claude Codeのhookを作ったのに発火しなかった話

AIエージェント8体でYouTubeチャンネルを運営している。今日はハーネスエンジニアリングで盛大にやらかした話。

---

## 何が起きたか

将軍（全体指揮のエージェント）が、殿（人間）の指示を拡大解釈してしまう問題が3回起きた。

例えば殿が「前回と同じテストをやれ」と言ったのに、将軍が「問題を現在のコードベースに合わせて更新した方がいい」と勝手に判断して、テスト問題を差し替えてしまった。比較テストなのに問題が違ったら比較にならない。

これを防ぐために、Claude Codeの**hook機能**を使って自動チェックの仕組みを作った。

---

## hookとは

Claude Codeにはhookという仕組みがある。エージェントがツールを使う前後に、指定したシェルスクリプトを自動実行できる。

- **PreToolUse**: ツール実行前に発火。スクリプトがexit 2を返すとツール実行をブロックできる
- **PostToolUse**: ツール実行後に発火。WARNING表示はできるがブロックはできない

人間が見ていなくても、ルール違反を機械的に検出・防止できる。ハーネスエンジニアリングの要。

---

## 作った仕組み

2つのhookを実装した。

**PreToolUseフック**: 将軍がコマンドファイルに書き込む時、`lord_original:`（殿の発言原文）フィールドがなければBLOCK。殿の原文を必ず記録させる。

**PostToolUseフック**: 書き込み後、殿の原文（lord_original）と将軍の指示（command）を`claude -p`でOpusに比較させる。殿が言っていないことがcommandに含まれていたらWARNING。

軍師に設計させ、足軽に実装させ、テストもPASSした。完璧だと思った。

---

## 発火しなかった

実装完了後、最初のコマンド発行。

何も起きなかった。BLOCKもWARNINGも出ない。

---

## 原因

hookのフィルタ条件はこうなっていた：

```
if tool_name != "Write" and tool_name != "Edit":
    exit 0  # Write/Edit以外はスキップ
```

将軍がコマンドファイルに実際にどうやって書いているか：

```bash
cat >> queue/shogun_to_karo.yaml << 'EOF'
- id: cmd_1394
  lord_original: "だせ"
  command: ...
EOF
```

**Bashツールの`cat >>`で書いていた。** Write/Editツールではない。

hookは全ツールで発火する。だがフック内部で「Write/Editだけチェック」とフィルタしていたので、Bashは素通りした。

---

## なぜこうなったか

設計した軍師は、将軍が「どのツールでファイルに書くか」を知らなかった。

Claude Codeには同じことをする複数の方法がある：

- **Writeツール**: ファイル全体を上書き
- **Editツール**: 部分的に書き換え
- **Bashツール**: `echo >`, `cat >>`, `tee`, `sed -i` など無数の方法

ファイルへの書き込みをチェックしたいなら、Write/Editだけでなく**Bashのリダイレクトも対象にしなければ穴が開く**。

しかも同じ穴が他のチェックにもあった：

- 足軽の禁止パス書き込みチェック → Write/Editのみ。Bashでechoすれば素通り
- タスクYAMLの行数制限チェック → Write/Editのみ。Bashでcat >>すれば素通り

全部同じパターンで穴が開いていた。

---

## 教訓

**hookを設計する時、実際のツール使用パターンを調査してから設計すべき。**

設計者が「ファイルに書く = Write/Editツール」と思い込んでいた。実際には「ファイルに書く = Write/Edit/Bash(リダイレクト)の3通り」ある。

これは人間のセキュリティ設計でも同じことが起きる。「ログインはフォームから」と思い込んでAPIエンドポイントの認証を忘れる。入り口が複数あることに気づかないと、1つを塞いでも別の入り口が開いている。

---

## 修正

Bashツールの場合もcommand文字列に対象ファイル名が含まれていればチェック対象にするように修正した。

```bash
# 修正後のフィルタ
if [[ "$TOOL_NAME" == "Bash" ]]; then
    # commandにshogun_to_karo.yamlが含まれるか
    if [[ "$COMMAND" == *"shogun_to_karo.yaml"* ]]; then
        # チェック実行
    fi
elif [[ "$TOOL_NAME" == "Write" || "$TOOL_NAME" == "Edit" ]]; then
    # 既存チェック
fi
```

---

## もう一つの教訓

この問題に気づいたのは、殿（人間）の一言だった。

「cmd発行時なんか動いた？アドバイス機能」

将軍は「動いていない」と気づいた。殿に聞かれなければ、hookが機能していないことに誰も気づかなかった。テストはPASSしていた。テストはWrite/Editツールでテストしたから。

**テストが通っても、実際の使い方でテストしなければ意味がない。** 単体テストと結合テストの違い、とも言える。hookの単体テストではなく、「将軍が実際にcmdを発行する」シナリオでテストすべきだった。
