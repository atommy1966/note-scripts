# マルチエージェントの"伝言ゲーム問題"と対策

## はじめに

7体のAIエージェントで開発チームを組んでいる。

```
殿（人間） → 将軍（戦略） → 家老（管理） → 足軽（実行）
```

問題は、**4段階の伝達で情報が劣化する**こと。殿が「リファレンス画像を使って漫画パネルを生成しろ」と言った。足軽に届いた頃には「画像を生成しろ」になっていた。リファレンスの概念が消えた。

これは組織の「伝言ゲーム問題」そのものだ。

## 実例: リファレンス画像が消えた

### 殿の指示

```
殿: 「リファレンス貼り付け成功しているがそれを利用していない。
      ファイル名指定してやらないと無駄」
```

明確だ。「--ref-image オプションでファイルパスを指定できるようにしろ」。

### 将軍がcmdに書いた内容

```yaml
purpose: "cdp_gemini_image_poc.pyに--ref-imageを追加し、
          ファイルパス指定でリファレンス画像をClipboard貼り付けして
          から画像生成できるようにする"
```

ここまでは正しい。

### 家老が足軽に伝えた内容

```yaml
task: "--ref-image引数を追加してテスト"
```

「Clipboard貼り付け」の詳細が消えた。テスト方法も曖昧。

### 足軽がやったこと

`ref_attached: true` と報告。しかし**実際にはリファレンスが効いていなかった。** refあり/なしで同一画像が出力された。足軽はログに `true` と出たからPASSと判断した。

### 殿が発見

```
殿: 「有り無しで画像が変わりません。失敗しているかと」
```

4段階の伝達で以下が失われた：
1. 「なぜリファレンスが必要か」の文脈
2. 「どうやってテストすべきか」の検証基準（画像のバイナリ比較）
3. 「成功とは何か」の定義（見た目が変わること）

## なぜ情報が劣化するか

### 1. 要約による情報損失

将軍が殿の指示を要約してcmdに書く。家老がcmdを要約してsubtaskに書く。毎回要約するたびに文脈が落ちる。

```
殿: 「リファレンス貼り付け成功しているがそれを利用していない。
      ファイル名指定してやらないと無駄」
      ↓ 将軍が要約
cmd: 「--ref-imageを追加し画像生成できるようにする」
      ↓ 家老が要約
subtask: 「--ref-image引数を追加してテスト」
```

### 2. 暗黙知の非伝達

殿は「画像を見れば分かるだろ」と思っている。将軍も分かる（殿と直接話しているから）。しかし足軽は殿の意図を直接聞いていない。「ref_attached: true → PASS」という形式的判断になる。

### 3. 検証基準の欠落

cmdのacceptance_criteriaに「--ref-imageオプションが使えること」とは書いてある。しかし「refあり/なしで出力画像が異なること」は書いていない。足軽は書いてある基準だけチェックする。

## 対策

### 対策1: 殿の原文をそのまま伝達する

我々のルールブック（CLAUDE.md）にはこう書いてある：

```
殿の原文を加工せず伝達する。
cmdのcommandフィールドに殿の発言原文を含め、
将軍が要約・解釈で薄めない。
```

cmdに `## 殿の指示（原文）` セクションを設けて、殿の発言をそのまま貼る。

```yaml
command: |
  ## 殿の指示（原文）
  「リファレンス貼り付け成功しているがそれを利用していない。
    ファイル名指定してやらないと無駄」
```

足軽は原文を読める。要約で失われた文脈を補完できる。

### 対策2: 検証基準を機械的に定義する

「テストしろ」ではなく、検証コマンドまで書く。

```yaml
acceptance_criteria:
  - "refあり/なしで画像を生成し、md5sumが異なること"
  - |
    検証コマンド:
    md5sum work/ref_test/*.jpg work/no_ref_test/*.jpg
    → ハッシュが全て異なること
```

足軽に判断させない。コマンド実行して結果を見るだけ。

### 対策3: 委任段数を減らす

CDPのような不安定な外部連携は、4段階の伝達に耐えない。将軍が直接やった方がいい場合もある。

```
Before: 殿 → 将軍 → 家老 → 足軽（4段、情報劣化）
After:  殿 → 将軍（直接実行、2段、情報維持）
```

実際、将軍が直接CDP漫画パネル生成をやったら、殿のフィードバックを即座に反映して1日で完成した。足軽に任せていたら何日かかったかわからない。

**ただし、将軍が全部やるのはスケールしない。** 判断基準：
- 殿との対話が必要な作業 → 将軍が直接
- 定型作業（テスト実行、ビルド等） → 足軽に委任
- 不安定な外部連携の初回 → 将軍が仕組みを作り、足軽はそれを使う

### 対策4: 共通ルールを設定ファイルに切り出す

プロンプト設計のルール（遠景禁止、セリフ配置等）をスクリプトにハードコードすると、足軽が知らないルールが適用されたりされなかったりする。

YAMLの設定ファイルに全ルールを書き、スクリプトがそれを読む。誰が実行しても同じルールが適用される。伝言ゲームの余地がない。

## 結果

| 対策 | 劣化する情報 | 防ぎ方 |
|------|------------|--------|
| 原文伝達 | 文脈・意図 | 殿の発言をそのまま含める |
| 機械的検証 | 成功基準 | コマンドで検証、判断させない |
| 委任段数削減 | 全て | 直接やる（スケールしないが確実） |
| 設定ファイル化 | ルール | 誰が実行しても同じ |

## まとめ

マルチエージェントの伝言ゲーム問題は、人間の組織の問題と本質的に同じだ。

- マネージャーが「お客さんこう言ってた」と要約する → 開発者に意図が伝わらない
- 仕様書に「テストすること」と書く → 何をテストするか不明
- 手順書に「適切に対応」と書く → 人によって解釈が違う

AIでも人間でも、対策は同じ：**原文を残す。基準を機械化する。伝達段数を減らす。ルールを設定化する。**

そして最も重要なのは、**伝言ゲームが発生していること自体に気づくこと。** 「足軽がダメだ」ではなく「伝え方が悪い」。
